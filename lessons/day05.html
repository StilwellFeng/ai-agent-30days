    工具调用：让 Agent 长出“手脚”

    LLM 只会“说”，工具让它能“做”。这是 Agent 区别于聊天机器人的关键一步。

    🎯 目标：理解 Function Calling 闭环与安全边界 ⏱ 预计 30 分钟 📖 无代码（有示意）

    还记得 Day 2 里 LLM 的三个短板吗？没有实时信息、不能精确计算、不能自己行动。工具（Tools）就是来补这三个短板的：LLM 负责“想”，你的程序负责“做”。

    核心机制：Function Calling（函数调用）

    别被英文吓到，机制一句话就能讲清：模型不直接执行任何操作，它只是输出一段“我想调用某某工具、传这些参数”的结构化指令，由你的程序真正去执行，再把结果还给它。

    工具长什么样？—— 先看“工具清单”

    一个 Agent 能调哪些工具，通常由开发者提前“注册”好。常见工具类型：

    工具典型能力解决 LLM 的哪个短板
    网络搜索查最新信息、新闻、网页知识过期 / 无实时信息
    计算器 / 代码执行精确计算、跑脚本、处理数据算不准、不会真执行
    API 连接器天气、地图、支付、企业系统接触不到外部系统
    文件读写读 PDF/Excel/Word，生成文档处理不了私有文件
    数据库查询查业务数据拿不到企业内部数据
    消息/邮件发通知、发邮件无法替用户“办事”

    程序怎么“告诉”模型有哪些工具？

    每个工具都会配一份“说明书”（名称、功能、参数），随请求一起发给模型。示意（不同平台的写法略有差异，以官方文档为准）：

    {
  "name": "get_weather",
  "description": "查询指定城市的实时天气",
  "parameters": {
    "city":   { "type": "string", "description": "城市名，如：北京" },
    "date":   { "type": "string", "description": "日期，默认今天" }
  }
}

    模型看完清单后，如果觉得需要查天气，就会“回答”一段类似 调用 get_weather(city="北京") 的指令，而不是直接编一个天气给你——这就是从“聊天”到“干活”的转折点。

    工具不是越多越好

    • 工具清单太长 → 模型“选择困难”，容易挑错、变慢、更费 Token。
    • 工具描述要写清楚“什么时候用它、什么时候别用它”。
    • 同名工具、模糊描述会让模型误调用——质量 > 数量。
    🔐 安全边界（今天就要建立的意识）：
    • 最小权限：只给 Agent 完成任务所需的最小工具权限，别一上来就开放“删文件”“转账”。
    • 危险操作人工确认：付款、发邮件、删除等操作，设计成“先征求用户同意”。
    • 输入校验：工具收到的参数可能被恶意构造（Prompt 注入），程序侧要做校验与白名单（第 29 天专题）。
    • 可观测：记录 Agent 每一步调了哪个工具、传了什么参数，出问题才能查。

    ✍️ 今日练习（约 10 分钟）

    1. 打开一个支持联网/工具的 AI 助手，问一个“只有查了才知道”的问题（如“今天上海有什么展览”），观察它是否先搜索再回答。
    2. 针对你 Day 1 记下的那个任务，列出它需要哪 3 个工具，每个工具写一句“描述”和需要的参数。
    3. 想一想：其中有没有“危险工具”？你会怎么加一道人工确认？

    📌 今日小结

    Function Calling模型输出“调哪个工具、传什么参数”的指令，程序真正执行 闭环LLM 决定 → 程序执行 → 结果回填 → LLM 基于真实结果作答 工具的意义补上 LLM 的实时性、精确性、行动力短板 铁律最小权限 · 危险操作人工确认 · 输入校验 · 全程可观测
